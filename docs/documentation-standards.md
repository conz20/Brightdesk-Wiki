# Documentation standards

The wiki exists to make Brightdesk easier to understand and use. Every page should help a reader find an answer, complete a task or understand a product accurately.

## Write for the reader
- Use plain, direct English.
- Prefer short sentences and familiar words.
- Explain a technical term the first time it appears.
- Use descriptive headings that match the question a reader might ask.
- Give one action per numbered step.
- Use exact labels from the current interface.
- Include a practical example when it makes the instruction clearer.

## Separate customer and technical information
Customer pages explain what to do. Technical pages explain how the software is built, tested and maintained. Do not put internal prompts, credentials, private reports or Brightdesk-AI internals in customer documentation.

## Evidence before claims
Use evidence in this order:
1. A verified running product workflow.
2. A passing test that covers the behaviour.
3. The current implementation in the product repository.
4. An approved specification or decision.

A README description alone is source evidence, not proof that a user workflow passes. Label the claim accordingly.

## Images and examples
- Use genuine screenshots only after the relevant workflow has been tested.
- Label mock-ups as interface design artwork.
- Use fictional sample names and information.
- Add useful alternative text to images.
- Do not copy Craft Wiki branding, assets, code or distinctive visual design.

## Keeping pages current
When a product source, test, release or approved decision changes, identify affected wiki pages. Re-check steps and links. Update the page's source and verification date. If the change cannot be verified, mark it **Needs review** rather than silently presenting old instructions as current.

## Review checklist
- [ ] The page answers one clear reader question.
- [ ] The title and headings are easy to understand.
- [ ] Steps use exact, verified interface labels.
- [ ] Claims have a source.
- [ ] Planned and unavailable features are clearly labelled.
- [ ] Examples use fictional data.
- [ ] Images are correctly labelled.
- [ ] Related links work.
- [ ] Verification details and date are present.
